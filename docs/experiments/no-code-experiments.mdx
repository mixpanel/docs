Web Experiments let you build and launch A/B test variants on your website through a visual editor, with no code deploy per test. You open the page you want to test, click the element you want to change, edit it directly or describe the change to Mixpanel Agent, then launch.

<Callout icon="flask" iconType="regular" color="#5F41CF">
  **Beta.** Web Experiments is currently available to all customers during Beta.
</Callout>

## Beta Scope

| | Supported in beta |
| --- | --- |
| Browser for authoring | Chrome only |
| Install method | `mixpanel-browser` 2.86.0 or later, from npm |
| Site type | Best suited to static and marketing sites |

Complex single-page apps are better served by a feature experiment. Mutations are applied to the rendered DOM, so the more dynamic the page, the less predictable the result. The visual editor re-applies mutations when elements re-render, but a heavily client-routed app will still behave less reliably than a static page.

Authoring is Chrome-only. The experiment itself runs for all of your end users in any browser, because the variant is delivered by the Mixpanel JavaScript SDK rather than by the extension.

## Web vs Feature Experiments

Mixpanel has two experiment types. You choose one at creation time.

| | Web Experiment | Feature Experiment |
| --- | --- | --- |
| Variants built in | The visual editor, on your live site | Your codebase |
| Code change per test | None | Yes |
| Who can run it | Anyone with the right permissions | Requires an engineer |
| Best for | Copy, styling, and layout changes | Backend logic, new components, anything data-driven |

Web Experiments run on [Mixpanel Feature Flags](/docs/featureflags), and the visual editor creates and configures the flag for you. You do not write any flag evaluation code, and you do not need an engineer to implement the flag. The one-time SDK setup is the only code change the feature requires.

<Note>
  The experiment type can't be changed after the experiment is created. If you need to convert a test, create a new experiment.
</Note>

## Setup

Setup is a one-time job. After it's done, anyone with permission can create and launch experiments without touching code again.

<Steps>
  <Step title="Turn on Web Experiments in the SDK">
    Install version 2.86.0 or later of the Mixpanel JavaScript SDK:

    ```bash
    npm install --save mixpanel-browser@^2.86.0
    ```

    Then add `flags: true` and `visual_experiments: true` to your existing `init` call:

    ```javascript
    import mixpanel from 'mixpanel-browser';

    mixpanel.init('YOUR_PROJECT_TOKEN', {
      // ...your existing options
      flags: true,
      visual_experiments: true,
    });
    ```

    Both `flags` and `visual_experiments` are required. Feature Flags is the mechanism that delivers variants to your users, so Web Experiments will not run without it.
  </Step>

  <Step title="Install the Chrome extension">
    Install the latest [Mixpanel extension](https://chromewebstore.google.com/detail/mixpanel/camknfenboildigjgpmhojlcnejppooh) from the Chrome Web Store.

    After installing, refresh your Mixpanel tab. Mixpanel checks for the extension when the page loads, so without a refresh it will keep reporting the extension as missing.
  </Step>

  <Step title="Create the experiment">
    From the Experiments report, create a new experiment and choose **Web Experiment**. Enter the URL of the page you want to test in **Visual Editor URL**, then configure variants, success metrics, and duration the same way you would for any experiment. See [Setup & Launch Your Experiment](/docs/experiments#setup--launch-your-experiment) for those settings.
  </Step>

  <Step title="Design your variants">
    Click **Edit in Editor** to open your site with the visual editor overlaid on it. Design each variant, save, and launch.
  </Step>
</Steps>

## Designing Variants

The editor opens your live site in a new tab with a toolbar for switching between variants and adding new ones. Select an element to edit it, or open Mixpanel Agent and describe the change you want.

### What You Can Change

| Change | Notes |
| --- | --- |
| Text | Replaces the element's text. Markup is not parsed. |
| Colors | Fill and gradient, through a color picker |
| Other CSS | Any CSS property, set as an inline style |
| CSS classes | Add or remove classes |
| Attributes | Including `src`, which is how you swap an image |
| Hide | Removes the element from the page for that variant |

Editing raw HTML is not currently supported. Moving, reordering, inserting, and duplicating elements are not available yet.

### Editing With Mixpanel Agent

Mixpanel Agent can apply several changes at once from a single description, such as restyling a set of buttons and swapping the copy in different sections. Agent proposes the changes, you approve them, and they land in the changes list like any other edit. Agent can only author visual changes from inside the editor; the dashboard chat hands off to the editor instead.

### Reviewing and Removing Changes

Every edit is recorded in a changes list in the editor. You can review each change and delete it individually, which is also how you undo a change: e.g., to unhide an element, delete the hide change.

## Targeting a URL

A variant applies to a page when the page's origin and path match the URL saved for that variant.

- Query strings and hash fragments are currently ignored, so `/cart?utm_source=email` matches `/cart`
- A trailing slash is ignored, so `/cart/` matches `/cart`
- Matching is case-sensitive, so `/Cart` does not match `/cart`
- Wildcards, prefixes, and regular expressions are not yet supported

To test several pages, you currently need to create a separate experiment for each one.

### Overlapping Experiments

When you enter a URL that another draft or running web experiment already targets, Mixpanel warns you in case of potential conflicts. Overlapping web experiments can interfere with each other and make results hard to attribute. The warning does not block you from saving or launching, so it's on you to decide whether the overlap is acceptable.

## Permissions

Launching a web experiment requires the **Launch Web Experiments** permission, which is separate from the ability to create or edit one. This lets you open variant design up to a wider group while keeping control over what reaches your users.

| Role | Can launch web experiments |
| --- | --- |
| Owner | Yes |
| Admin | Yes |
| Analyst | Yes |
| Consumer | No |
| Billing Admin | No |

Grant it to a custom role under Organization Settings, in the **Feature Flags and Experimentation** group of project permissions. Without it, a user can design variants and save them, but the launch action stays disabled.

## Limits and Best Practices

<Warning>
  Variants you create from inside the editor start at a 0% traffic split and are served to nobody until you set their split on the experiment page in Mixpanel. Check your variant splits before you launch.
</Warning>

- Editing variants on a running experiment changes what live users see immediately and can skew your results
- An experiment can't launch until at least one variant has an edit
- Don't edit the flag variant values by hand for a web experiment; doing so breaks the editor
- Edits to elements inside dynamic feeds can be inherited by items that render later
- Visual changes are capped at 32KB per variant
- One editor session per user at a time. Opening the editor again ends the previous session
- Editor sessions expire after an hour
- Concurrent edits to the same variant overwrite each other, so coordinate before multiple people edit one experiment

<Warning>
  Like any client-side testing tool, Web Experiments can add page load latency and can cause flicker, where visitors briefly see the original page before the variant appears. Test your experiment on a staging site first and confirm that the impact is acceptable for your pages.
</Warning>

## Troubleshooting

### The Editor Reports the Extension Is Missing

Refresh the Mixpanel tab. Detection runs on page load. If it still fails, confirm you're on the latest extension and that older Mixpanel extensions are disabled.

### Changes Don't Appear on Your Site

Confirm that your site uses `mixpanel-browser` 2.86.0 or later and passes both `flags: true` and `visual_experiments: true` to `init`. The editor reports an error when it detects that Web Experiments are turned off in the SDK. Also check that the URL you're viewing matches the saved URL, keeping case sensitivity in mind.

## Launching and Reading Results

Launching and analysis work the same as any other experiment. Results appear in the Experiments report. See [Monitor Your Experiment](/docs/experiments#monitor-your-experiment) and [Interpret Your Results](/docs/experiments#interpret-your-results).

### When a Visitor Counts as Exposed

Assignment and exposure are separate, and only exposure puts a visitor in your results.

The SDK fetches flags on any page that loads it. That fetch returns a variant only for experiments whose targeting rules and traffic allocation the visitor qualifies for, and qualifying is what assigns them to a variant. A visitor outside the targeting or the rollout receives no variant at all.

Exposure is tracked later, when the SDK reads an assigned variant in order to apply its changes. That only happens on a page whose URL matches the one saved for the experiment, and the SDK sends an `$experiment_started` event at that point, once per experiment per page load.

So a visitor can browse your site without ever entering your results, either because they didn't qualify for the experiment or because they qualified but never reached a matching page. Neither case appears in your experiment results or counts toward your [Monthly Experiment Users](/docs/experiments#plan-availability).

Exposure events from a web experiment have the same shape as those from a feature experiment, so the Experiments report reads them identically.
