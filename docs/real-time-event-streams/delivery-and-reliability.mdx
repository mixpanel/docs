Real-Time Event Streams are designed for at-least-once delivery with automatic retry of transient failures. This page describes the delivery, retry policy, failed events log, and headers you can use to deduplicate on your side.

## Latency

Real-Time Event Streams target delivery to webhook endpoints within **p50 ≤ 60 seconds** of ingestion under normal load.

## Batching

Events are batched per Sync before delivery. Mixpanel sends a batch when it reaches the max batch size (500 events by default) or **5 seconds** after the first event in the batch, whichever comes first. The max batch size and the envelope template are configurable on the Destination.

By default, each batch is a single `POST` whose body is a JSON array of rendered events:

```json
[
  { "event": "Signup", "user_id": "abc" },
  { "event": "Signup", "user_id": "def" }
]
```

Your endpoint must return a single 2xx for the whole request. A failed request fails every event in it.

## Retry policy

Transient delivery failures are retried automatically. Permanent failures are not retried and surface as configuration errors.

### What gets retried

| Failure type | Retried? | Notes |
| --- | --- | --- |
| `5xx` response | Yes | Server-side error at the destination. |
| Connection timeout / network error | Yes | Includes DNS failures and TLS handshake errors. |
| `408 Request Timeout`, `425 Too Early` | Yes | Treated as a temporary problem at the destination. |
| `429 Too Many Requests` | Yes | Handled via backpressure. See [Rate limits](#rate-limits-and-backpressure). |
| `401`/`403` (auth) | No | Terminal auth failure. Sync is paused. |
| Other `4xx` response (for example `400`) | No | The destination rejected the request. See [4xx errors](#4xx-errors). |

### Backoff schedule

Up to **5 attempts** (1 initial + 4 retries) with exponential backoff starting at 200ms, totaling roughly **3 seconds** of delay:

| Attempt | Delay before attempt |
| --- | --- |
| 1 (Initial) | Immediate |
| 2 | 200ms |
| 3 | 400ms |
| 4 | 800ms |
| 5 | 1.6 seconds |

For `429` responses, the `Retry-After` header is honored when present, capped at 10 seconds.

### 4xx errors

`401` and `403` responses indicate an authentication failure. These are terminal:

- The Sync is paused immediately.
- The Destination surfaces an authentication error.
- A project admin must fix credentials or the webhook URL before restarting.

Other `4xx` responses (for example `400`), except `408`, `425`, and `429`, mean the destination rejected the request, so they are not retried. The events in that request are dropped and recorded in the [failed events log](#failed-events-log). See [Alerting on failure](#alerting-on-failure) for when repeated failures pause the Sync.

## Events that are not delivered

Mixpanel drops an event for a Sync, without retrying it, in these cases:

- **Payload too large.** The payload for an event is larger than **10 MB** after the Liquid template is applied.
- **Template render error.** The Liquid payload template fails to render for an event, for example because a property value has an unexpected type. Only that event is dropped for that Sync. Other events and other Syncs are unaffected.
- **Event too old.** The event's timestamp is more than **5 days** in the past. Real-Time Event Streams are for live events, so events with older timestamps, including imported historical data, are not streamed.

A temporary issue on Mixpanel's side is retried until it succeeds, so it delays delivery but does not lose events. Failures at your destination follow the [retry policy](#retry-policy) above.

If events are missing at your destination, contact Mixpanel Support.

## Failed Events Log

When events cannot be delivered, including after retries are exhausted, they are recorded in a **failed events log** retained in-product for debugging. Each entry is an aggregated roll-up: one row per Sync, status code, and error type, with the count of failed events in that window. To help you debug, each entry includes a sample event and, when a response was received, the response body from your destination.

## Alerting on failure

A Sync is paused when it hits a terminal failure: an authentication error (`401`/`403`), or more than 50% of its events failing to deliver within a 15-minute window. The Sync moves into the `error` state and stops streaming until a Project Admin re-enables it. See [States and monitoring](/docs/real-time-event-streams/states-and-monitoring) for state transitions.

## Rate limits and backpressure

When a destination returns `429 Too Many Requests`, the request is retried after respecting the `Retry-After` header (if present, capped at 10 seconds), or per the [backoff schedule](#backoff-schedule) otherwise. If retries are exhausted, the events are recorded in the [failed events log](#failed-events-log). See [Alerting on failure](#alerting-on-failure) for when repeated failures pause the Sync.

## What to build on your side

To get the most out of the delivery model:

- **Return 2xx quickly.** Acknowledge the request before doing heavy downstream work; process asynchronously on your side.
- **Return 4xx for permanent errors, 5xx for transient ones.** This lets Mixpanel retry the right failures and surface the right errors.
- **Honor `Retry-After`** on `429` responses so Mixpanel can back off cleanly.
