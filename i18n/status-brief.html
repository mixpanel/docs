Findings2

Two things worth knowing before anyone translates a page

Reframes M2 + M3

Mintlify already sells the pipeline we were about to build

Native AI translations — Pro and Enterprise — bulk-translates the docs and opens a PR in this repo on every change, never publishing without a human merge. That is M2's bulk translation plus all of M3.

Every signal says Mixpanel is on Enterprise: custom domain, custom CSS and JS, self-hosted Garnett fonts, 881 redirects — and the README puts the Mintlify web editor behind Okta, which is SSO, which is Enterprise. One person opening Settings → Translations settles it.

Changes the engine criteria

710 internal links will break silently the moment a heading is translated

Every heading anchor in this repo derives from its English text. Translate ## Anatomy of an Event and the anchor changes — so 710 deep links land at the top of the page instead of the right section. Nothing errors. Nothing shows in a diff.

The fix is mechanical — pin ## 이벤트의 구조 [#anatomy-of-an-event] — but the engine has to do it, and not every candidate can. It became the disqualifying criterion.

Half the volume sits in five sections. docs/tracking-methods alone is 91,529 words across 68 files — the biggest block, but the cheapest per word: the same headings recur 13–14× across every SDK, so translation memory and the glossary do most of the work. It should be reviewed as one batch by one reviewer.

Decisionopen

Which translation engine?

This is the one blocking decision. It should be settled before bulk translation starts, because the three paths produce different repos.

Mintlify native

  • Almost certainly already paid for
  • Implements M3 outright — PR per change, human gate
  • Zero repo surface, first-party MDX semantics
  • No published glossary or do-not-translate control
  • Silent on heading anchors and OpenAPI
Start here

General Translation

  • Mintlify's own docs repo runs on it
  • Pins heading anchors — solves the 710
  • Localizes docs.json nav automatically
  • Can localize the OpenAPI specs
  • Second vendor, second contract
Documented fallback

Lingo.dev

  • Cheapest per word; open source
  • No heading-anchor pinning
  • No docs.json nav localization
  • No OpenAPI localization
Not recommended

How to settle it in an afternoon. Twelve pages, chosen to cover every structural pattern in the corpus. Run each candidate over them and score with validate-mdx-parity.mjs — the answer comes out as a number, not an opinion. Then four human checks on those twelve only: glossary adherence, the 리텐션/데이터 보관 split, particles after Latin words, and register.

Three things that need a person

5 minutes

Open the Mintlify dashboard → Settings → Translations

If the page exists and lets you add a locale, DF-823 closes and the engine decision gets much easier. While there, capture whether the feature exposes any glossary or do-not-translate control — that single answer decides how much pipeline we build.

An afternoon

Run the 12-page bake-off

Scored by the validator, so it produces a number rather than a preference. Twelve pages to find out beats guessing across 295.

Name a person

Who reviews the Korean, and when?

Roughly 3–5 days per language, and the only step in the whole pipeline that does not compress. Worth settling before bulk translation runs, not after — machine output that sits unreviewed is not a shipped locale.

After Korean

The next language is probably Japanese

Mixpanel already publishes hreflang alternates for exactly four locales — en-US, ko-KR, ja-JP, id-ID. Marketing has already decided which non-English markets are worth translating for and paid for it. Docs should follow that list rather than invent a new one.

Do not extend past Japanese on inference. docs.json already reports into a Mixpanel project, so docs pageviews by locale — and the measured lift after /ko ships — are a report away. That one report also settles whether the API reference ever gets translated, for every language at once. We sell this product; we should use it.
