## Overview

Most rework in this phase traces back to two early choices: tracking too much, and putting off identity until data is already flowing. Both are easy to get right at the start and slow to fix later.

This phase has three parts:

- **Plan:** Decide which events to track and write them down.
- **Test:** Send your events to a development project and check them there.
- **Launch:** Move the same tracking to production and confirm it holds up.

**Done when:**

- You've picked a short list of events
- They check out in development
- They reach production

## Plan

Pick a handful of events to start with, and write them down so your team can build from them.

<Info>
  Using an AI coding agent? [Install with AI](/docs/quickstart/install-with-ai) can suggest events from your code and, if you want a full setup, draft your tracking plan too. You can use it instead of the tasks in this section.
</Info>

### Decide what to measure

Start from the questions you want answered, then pick a handful of events that answer them. What counts depends on your product: a fitness app might count a finished workout, and an e-signature tool a signed contract. [Measure Value](/guides/strategic-playbooks/guide-to-product-analytics/measure-value) · [What to Track](/docs/what-to-track)

<Tip>
  **Small doesn't mean thin.** Cover one journey from start to finish, not a scattering of events across the product.
</Tip>

### Choose your events

One event with properties beats one event per item. Skip personal data, and anything Mixpanel already collects. [How To Build a Tracking Strategy](/guides/guides-by-workflow/build-tracking-strategy) · [Default Properties](/docs/data-structure/property-reference/default-properties) · [Data Privacy & PII Best Practices](/guides/guides-by-workflow/data-privacy)

### Write down your first events

List the events you picked and the properties you want on each, in one place your engineer can build from. You don't need a complete tracking plan yet, so fill in only your first events and add to it as you grow. Have a teammate, or your Mixpanel contact if you have one, take a look before anyone builds. [Create A Tracking Plan](/docs/tracking-best-practices/tracking-plan)

<AccordionGroup>
  <Accordion title="New to events, users, and properties?">
    Start with how Mixpanel organizes data into events, users, and properties, so your plan uses the same terms. [Data Model](/docs/data-structure/concepts)
  </Accordion>

  <Accordion title="Selling to companies?">
    Decide whether to analyze them as groups, not just as users. [Group Analytics](/docs/data-structure/group-analytics)
  </Accordion>
</AccordionGroup>

## Test

Send your events to a development project and check them there, so mistakes never touch your real data.

<Info>
  Using an AI coding agent? Create your development project first, since you'll need its project token. Then [Install with AI](/docs/quickstart/install-with-ai) can do much of the rest of this section. It picks the right SDK, adds tracking and identity to your code, and checks that events arrive. You'll still deploy the changes to your testing environment.
</Info>

### Create development and production projects

Make one project for testing and one for your real data. [Managing Projects](/docs/orgs-and-projects/managing-projects) · [Developer Environments](/docs/tracking-best-practices/developer-environments)

### Choose how data gets in

Pick the method that fits how your product is built. [Tracking Methods](/docs/tracking-methods) · [Choosing the Right Method](/docs/tracking-methods/choosing-the-right-method)

### Send your first events

Install the SDK and send the events you picked to your development project. [Quickstart](/docs/quickstart) · [SDKs](/docs/tracking-methods/sdks) · [Tracking Best Practices](/docs/tracking-best-practices)

### Identify your users

Set up identity when you first send data. [Identity Management Overview](/docs/tracking-methods/id-management) · [Identifying Users (Simplified)](/docs/tracking-methods/id-management/identifying-users-simplified)

<Tip>
  **Pick a user ID that never changes before you write any identity code.** Once a user ID is set, it can't be changed.
</Tip>

### Check your events and identity

Developers check the code, and product teammates walk through the main user flows. Then build one report from your development data that answers a top question. [Ensuring Data Quality](/guides/guides-by-workflow/ensure-data-quality) · [Debugging](/docs/tracking-best-practices/debugging) · [Insights](/docs/reports/insights)

No events showing? [Sending Data FAQ](/troubleshooting/sending-data)

<AccordionGroup>
  <Accordion title="Thinking about autocapture?">
    Autocapture records page views and clicks on web without extra code. It can't tell which actions matter to your business, so use it alongside the events you picked, not instead of them.

    Events it records still count toward your billing, even if you hide them from reports, so check what it records for anything sensitive first. [Autocapture](/docs/tracking-methods/autocapture)
  </Accordion>

  <Accordion title="Tracking companies as groups?">
    If you chose to analyze companies as groups, set up your group keys as you send events. [Group Analytics Implementation Guide](/docs/data-structure/group-analytics/group-analytics-implementation)
  </Accordion>
</AccordionGroup>

## Launch

Move the same tracking to production and confirm it holds up with real users. Launch here means going live in production. Rolling Mixpanel out to your team comes in Phase 3.

<Info>
  Used [Install with AI](/docs/quickstart/install-with-ai)? You'll still launch to production through your usual release process. Review the code your agent wrote before you deploy it.
</Info>

### Switch to your production project

Point your product at your production project, and stop sending test data to your development project. [Locate Current Project Token](/docs/orgs-and-projects/managing-projects#locate-current-project-token)

### Deploy and compare

Review the code, deploy it through your usual release process, then compare what arrives with what you tested. [Missing or Incomplete Events](/docs/tracking-best-practices/debugging#missing-or-incomplete-events)
